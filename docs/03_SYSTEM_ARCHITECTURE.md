# Design Philosophy

The system architecture of Daily Routine Helper is designed to support long-term evolution while keeping the core planning experience simple.

The architecture should prioritize clarity, maintainability, and adaptability over unnecessary complexity.

## 1. The planning engine is the center of the system

All components exist to support the planning engine.

The user interface, memory, and data storage should serve the planning process rather than define it.

---

## 2. Business logic should remain independent from the user interface

Planning logic should be reusable across different interfaces.

The user interface is responsible for presentation, while planning decisions belong to the planning engine.

---

## 3. Planning context is more important than data storage

The purpose of persistence is not to collect user data.

It is to preserve the planning context required to generate increasingly personalized plans.

The architecture should store only the information necessary to improve future planning.

---

## 4. Design for evolution

The architecture should support future roadmap phases without requiring major redesigns.

New capabilities should extend the planning engine rather than replace it.

---

## 5. AI models are replaceable

The architecture should remain independent of any specific AI provider or model.

The planning engine should define the planning workflow, while language models serve as interchangeable reasoning components.

# System Overview

Daily Routine Helper is organized around a central planning engine.

Rather than allowing the user interface or database to drive the application, all planning decisions are generated by the planning engine using the user's planning context, long-term goals, and recent reflections.

The architecture separates user interaction, planning logic, and data persistence to ensure long-term maintainability and extensibility.

# Core Modules

Daily Routine Helper is composed of a small set of core modules. Each module has a clear responsibility, and business logic should remain separated from presentation and persistence.

## 1. Planning Engine

The Planning Engine is the core of the system.

It is responsible for:
- generating daily plans
- adjusting plans based on context
- explaining why a plan was generated
- coordinating the overall planning workflow

The Planning Engine should not depend on the user interface or database implementation.

---

## 2. Planning Context

Planning Context is the structured input used by the Planning Engine before generating a plan.

It may include:
- long-term goals
- recent execution results
- daily reviews
- planning history
- user preferences
- recurring behavioral patterns

Planning Context is not a raw data dump. It should contain only the information needed to support better planning decisions.

---

## 3. Goal Manager

The Goal Manager is responsible for maintaining the user's long-term goals.

It should:
- store and update goals
- organize goals by category
- provide goal information to the Planning Engine

The Goal Manager does not generate daily plans by itself.

---

## 4. Review Manager

The Review Manager is responsible for collecting and organizing daily reflections.

It should:
- record what was completed
- record what was not completed
- capture blockers
- capture tomorrow's focus

Its output becomes part of the Planning Context for future planning.

---

## 5. Presentation Layer

The Presentation Layer is responsible for user interaction and displaying results.

It should:
- show today's strategy and plan
- collect review input
- display long-term goal progress

It must not contain planning logic.

---

## 6. Data Storage

Data Storage is responsible only for persistence.

It should:
- save goals
- save planning history
- save reviews
- save user preferences

It must not make planning decisions.

# Data Flow

Daily Routine Helper follows a simple planning loop.

The system collects long-term goals, recent execution results, and reflection history, then combines them into planning context before generating today's plan.

## 1. Goal Input

The user defines long-term goals through the interface.

These goals are stored by the Goal Manager and remain available as the foundation for future planning.

Examples include:
- Career goals
- Health goals
- English learning goals

---

## 2. Daily Review Input

At the end of the day, the user completes a short review.

The Review Manager captures:
- what was completed
- what was not completed
- the biggest blocker
- tomorrow's focus

This review is stored as part of the user's planning history.

---

## 3. Planning Context Assembly

Before generating a new plan, the system assembles Planning Context from available sources.

Planning Context may include:
- long-term goals
- recent reviews
- planning history
- user preferences
- recurring behavioral patterns

This context is prepared specifically for the Planning Engine.

---

## 4. Daily Plan Generation

The Planning Engine uses Planning Context to generate today's plan.

The plan should:
- remain realistic
- be measurable
- stay aligned with long-term goals
- reflect recent execution and reflection

The output is then passed to the Presentation Layer.

---

## 5. User Execution

The user follows the plan during the day.

The system does not enforce execution.
It acts as a planning companion and allows the user to adjust when reality changes.

---

## 6. Daily Reflection and Learning

At the end of the day, the user reflects on execution again.

The new review is stored and becomes part of the next Planning Context.

This creates a continuous feedback loop:

Long-term Goals
→ Planning Context
→ Daily Plan
→ Execution
→ Review
→ Updated Planning Context
→ Next Daily Plan

# Data Model

Daily Routine Helper stores only the information needed to support better planning.

The data model should be minimal, structured, and focused on planning context rather than raw data accumulation.

## 1. UserProfile

The UserProfile contains stable user-level preferences and configuration.

It may include:
- preferred planning style
- preferred review style
- default task load
- category priorities
- AI behavior preferences

This data changes infrequently.

---

## 2. LongTermGoal

A LongTermGoal represents a meaningful objective the user wants to pursue over time.

Examples:
- prepare for fall recruiting
- build a sustainable exercise habit
- improve spoken English

Each goal should include:
- id
- title
- category
- description
- priority
- status
- createdAt
- updatedAt

---

## 3. DailyPlan

A DailyPlan represents the plan generated for one specific day.

Each plan should include:
- date
- linked long-term goals
- planning rationale
- plan items
- expected workload
- creation timestamp

The DailyPlan is the output of the Planning Engine.

---

## 4. DailyPlanItem

A DailyPlanItem is a single measurable task inside a DailyPlan.

Each item should include:
- id
- title
- category
- completion criteria
- notes
- status

Examples:
- expand one project story
- complete one workout
- collect 10 new English expressions

---

## 5. DailyReview

A DailyReview captures what happened during execution.

Each review should include:
- date
- completed items
- incomplete items
- biggest blocker
- tomorrow focus
- reflection notes

The DailyReview becomes part of future Planning Context.

---

## 6. PlanningPattern

A PlanningPattern represents a recurring behavior or tendency inferred from review history.

Examples:
- English tasks are often postponed in the evening
- career tasks require more time than expected
- workout plans are more likely to succeed in the morning

Patterns should be derived from history and used to improve future planning.

---

## 7. PlanningContextSnapshot

A PlanningContextSnapshot is the structured context assembled before plan generation.

It may include:
- long-term goals
- recent reviews
- planning patterns
- user preferences
- recent workload trends

This is the information passed to the Planning Engine when generating today's plan.

---

## 8. GeneratedExplanation

A GeneratedExplanation stores the reasoning shown to the user with a plan.

It should explain:
- why these tasks were selected
- why the workload is set at this level
- how today's plan connects to long-term goals

This helps the user understand the planning process and gradually become a better planner.

---

## Data Model Principle

The system should store only what is necessary to improve future planning.

It should avoid collecting data that does not help the Planning Engine make better decisions.

# AI Planning Engine

The AI Planning Engine is the core decision-making component of Daily Routine Helper.

Its responsibility is to transform Planning Context into a realistic, measurable, and goal-aligned daily plan.

The planning engine is not a task manager and not a generic chat assistant.
It exists specifically to support adaptive daily planning.

## Responsibilities

The AI Planning Engine is responsible for:

- interpreting long-term goals
- reading the current Planning Context
- identifying the most relevant priorities for today
- generating a realistic daily plan
- balancing workload across categories
- explaining why the plan was generated
- adapting to recent execution patterns and reflections

---

## Inputs

The planning engine receives structured planning input such as:

- long-term goals
- recent reviews
- planning patterns
- user preferences
- workload trends
- category priorities
- today's external constraints, if available

The engine should use only the context needed for planning.
It should not depend on unrelated raw data.

---

## Outputs

The planning engine produces:

- a DailyPlan
- DailyPlanItems with completion criteria
- a short planning rationale
- an explanation of how today's plan connects to long-term goals

The output should be understandable to the user and easy to act on.

---

## Planning Rules

The AI Planning Engine should follow these rules:

1. Plans must be realistic and achievable.
2. Plans must be measurable.
3. Plans must reflect the user's current context.
4. Plans should remain aligned with long-term goals.
5. Plans should be adjusted based on execution history and reflection.
6. The engine should reduce planning friction rather than maximize task count.

---

## Behavioral Expectations

The AI Planning Engine should:

- avoid generating overly ambitious plans
- avoid treating every day as independent
- prefer continuity over randomness
- adapt workload when the user has been over- or under-loaded
- explain why certain tasks are prioritized over others

The engine should behave like a planning system that learns over time.

---

## Separation of Concerns

The AI Planning Engine should not be responsible for:

- rendering the user interface
- storing data directly
- managing navigation
- handling presentation logic
- deciding how the product looks

Its job is to make planning decisions, not UI decisions.

---

## Planning Output Principle

The output of the planning engine should help the user answer three questions:

- What should I do today?
- Why is this the right plan?
- How does this help my long-term goals?

If the output cannot answer these questions clearly, the planning result is not good enough.

# UI Layer

The UI Layer is responsible for presenting planning information and collecting user input.

It should help the user plan quickly, review easily, and stay focused on long-term goals.
The UI Layer must not contain business logic or planning decisions.

## Design Principles

The UI should:

- keep planning lightweight
- reduce cognitive burden
- make the current state easy to understand
- surface only the most relevant information
- support daily use without unnecessary complexity

---

## 1. Dashboard

The Dashboard is the main daily entry point.

It should show:
- today's focus
- today's plan
- short planning rationale
- quick access to review and settings

The Dashboard should answer:
- What should I do today?
- Why is this the plan?
- What should I do next?

The Dashboard should be simple, readable, and optimized for daily use.

---

## 2. Daily Review View

The Daily Review View is used at the end of the day.

It should collect:
- completed tasks
- incomplete tasks
- biggest blocker
- tomorrow's focus
- optional reflection notes

The review interface should be lightweight enough to complete in a few minutes.

---

## 3. Goal Management View

The Goal Management View is used to define and update long-term goals.

It should allow the user to:
- create goals
- edit goals
- organize goals by category
- adjust goal priority

This view should remain simple and focused on long-term planning foundations.

---

## 4. Planning History View

The Planning History View is used to review previous plans and reflections.

It should help the user:
- understand past execution
- notice recurring patterns
- see how plans have evolved over time

This view supports reflection and long-term learning.

---

## 5. Settings View

The Settings View is used to configure planning preferences.

It may include:
- planning style preferences
- review style preferences
- workload preferences
- category priorities
- AI behavior preferences

The settings should influence planning behavior without overwhelming the user.

---

## UI Layer Principle

The UI Layer should present the planning system clearly, but it should never determine planning logic.

The interface exists to support the Planning Engine, not replace it.

# Future Extensibility

The architecture should support the roadmap without requiring major redesigns.

The goal is to ensure that future capabilities can be added by extending the existing system rather than replacing it.

## Extensibility Principles

The system should be designed so that:

- new planning signals can be added to Planning Context
- new review types can be added without changing the core loop
- new planning behaviors can be introduced without rewriting the Planning Engine
- new interfaces can reuse the same business logic
- future integrations can be connected through structured context rather than hard-coded dependencies

---

## Phase 2 Support — Personalized Planning

The architecture should support the system learning more about the user over time.

This means it should be easy to add:
- weekly reviews
- recurring pattern detection
- richer planning history
- more detailed planning adjustments

These additions should improve how the Planning Engine understands the user without changing the core daily workflow.

---

## Phase 3 Support — Planning Coach

The architecture should support more explanatory and reflective interactions in the future.

This means it should be possible to add:
- strategy discussions
- reflection summaries
- planning explanations
- coach-like guidance

These features should build on top of the existing planning system rather than replacing it.

---

## Phase 4 Support — Life Integration

The architecture should allow external context to be introduced gradually.

This means it should be possible to integrate:
- calendar events
- reminders
- external productivity tools
- knowledge base systems

These integrations should feed structured context into the planning engine instead of taking over the planning process.

---

## Future Growth Principle

Every future feature should strengthen the core planning loop:

Long-term Goals
→ Planning Context
→ Daily Plan
→ Execution
→ Review
→ Updated Planning Context

If a new feature does not improve this loop, it should be treated as optional or out of scope.
